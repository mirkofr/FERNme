# v0.3 — recall latency and the bounded working set

Prompted by a real question on r/AI_Agents: *"spreading activation on every recall
sounds great until it adds 200ms+ to each turn. What's the p95 on a 50k-node graph?
That's the number that decides real-time agent vs research toy."*

Fair question. This doc records what we measured, what we fixed, and the honest
remaining work.

## What we measured (before any fix)

Synthetic, pure-Python, single graph. `user memories` = one person's own attributes;
`assoc edges` = the shared per-site co-occurrence graph.

| user memories | assoc edges | p95 |
|---|---|---|
| 30 | 500 | 2 ms |
| 100 | 2,000 | 34 ms |
| 200 | 5,000 | **222 ms** |

So the commenter was right about the implementation: at a few hundred memories it
crossed 200ms. Root cause was not the *algorithm* but the *data structure*:
`AssocGraph.neighbors()` scanned **every** association edge on every node, every hop —
O(user_nodes × assoc_edges × hops).

## Fix shipped in this change — adjacency index

`AssocGraph` now keeps a parallel `_adj` index (`node -> {neighbor: weight}`) built
lazily on first read and kept in sync by `set_edge()`. `neighbors()` is now O(degree),
not O(all edges). Same numbers after the fix:

| user memories | assoc edges | p95 (indexed) |
|---|---|---|
| 200 | 5,000 | 2.4 ms (was 222) |
| 500 | 50,000 | 28 ms |
| 1,000 | 50,000 | 30 ms |

A regression test (`tests/test_perf_recall.py`) asserts recall stays under a ceiling so
the O(E) scan can't silently come back. ~90× faster at 200 memories; usable for a
real-time agent across a 50k-edge shared graph.

## The honest remaining limit — one huge single-user graph

The index fixes the common case (shared graph growth, normal per-user sizes). It does
**not** make one person with 50k of their *own* memories fast:

| one user's memories | p95 (indexed) |
|---|---|
| 1,000 | 3 ms |
| 5,000 | 31 ms |
| 15,000 | 72 ms |
| ~50,000 | ~240 ms (extrapolated) |

Because `spread()` initializes activation over **every** stored memory and seeds the
frontier with all of them, recall is O(user_memories) regardless of the index. At 50k
own-memories it lands back near 200ms.

Two honest responses to that:

**1. A single person shouldn't *hold* 50k durable memories — that's what forgetting is
for.** FERNme's thesis is that weak/old memories decay and get pruned; a 50k personal
graph means decay never fired, which is the bug to fix, not the latency. Humans don't
keep 50k retrievable preferences either.

**2. Recall should not walk the whole graph anyway.** The scalable design is a
**bounded working set**.

## Proposed design: bounded working set + cold tier (not yet built)

Goal: recall cost depends on the *active neighborhood*, not lifetime memory count, so
p95 stays flat as a user's history grows.

- **Hot / cold split.** Keep a bounded "hot" set (recent + strong + high-salience
  memories, capped at e.g. a few hundred to ~1–2k). Everything else is "cold": persisted,
  not walked on every turn.
- **Seed-local activation.** `spread()` initializes activation only over `seeds ∪
  k-hop neighborhood ∪ hot set`, instead of over all of `ug.edges`. Cold memories enter
  only if an association pulls them in.
- **Consolidation / eviction.** Periodically (a batch job, no LLM): promote
  repeatedly-reinforced memories to hot, demote stale low-salience ones to cold. This is
  the same consolidation already sketched in the multi-timescale (fast/slow) work.
- **Cold reactivation.** A cold memory can be pulled back to hot when its attribute is
  directly observed again (cheap index lookup), so nothing is permanently lost — just
  paged out.

Expected effect: a user with 50k lifetime memories but a ~1k hot set recalls in
single-digit ms, because only the hot set + activated neighborhood is ever traversed.
Brain-analogous: you don't fire every memory you've ever formed on each thought.

## Status — built vs designed

- **Built + tested (this change):** adjacency index, O(degree) `neighbors()`, perf
  regression test, full suite green (99 tests).
- **Designed, not built:** the bounded working set / hot–cold tier. It's the real answer
  for the pathological single-large-graph case and the next scaling milestone. No
  benchmark is claimed for it yet.

## One-line answer for the thread

The index makes recall ~30ms p95 at 1k memories over a 50k-edge shared graph (was 222ms
at 200). For the degenerate "one user, 50k own memories" case, the answer is a bounded
working set + decay so recall only ever walks the active neighborhood — designed, not
yet built, and honestly labeled as such.
